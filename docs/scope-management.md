# 模块内作用域管理

使用当前 libxposed service 102 的 `getScope`、`requestScope` 和 `removeScope`。
开启会请求框架授权，是否批准由框架及用户决定；关闭直接移除当前用户作用域。
不自动开启系统框架，也不推导桌面 Hook 的系统框架依赖。

首页应用列表从 APK 的 `META-INF/xposed/scope.list` 读取，去重并过滤未安装应用，
统一使用 PackageManager 获取 ApplicationInfo、名称和图标，按 FLAG_SYSTEM / FLAG_UPDATED_SYSTEM_APP
区分“系统组件”和“应用作用域”，不再只把三个有模块设置的应用视为系统组件。
系统框架保留“系统框架”名称，从 android 包取得图标，传给 libxposed 的作用域名称仍为 `system`。
两组内部均按“有模块内设置、有应用内设置、其他应用”依次排序，同类按名称及包名排序。
只有包含模块内设置的系统框架、SystemUI、小米桌面进入二级页面，其作用域开关仍置于二级页面；
其他系统应用与普通应用使用相同卡片，直接显示作用域开关，无二级入口。

普通应用卡片上的开关只管理作用域；支持应用内设置的卡片另有“应用内设置”按钮，
沿用原有 Intent 入口，点击不会同时开关作用域。Telegram Plus 的推荐作用域包名修正为
`org.telegram.plus`，补齐已经支持的 beta 与 Nagram X 分支。

`ScopeManager` 在主线程发布状态、后台串行执行 IPC，service 绑定和 Activity 恢复时刷新。
等待批准时不乐观更改开关，批准或失败后重新查询框架；失败显示原因，查询失败时禁用编辑。
框架会替换同一模块未完成的授权请求，因此等待期间一次只处理一个作用域操作。
服务切换后忽略旧回调；管理器由 App 持有，Activity 重建不会丢掉等待中的请求。
作用域状态不写进配置缓存。修改作用域不会卸载已有 Hook，需重启目标应用使其生效。

验证包括：授权等待与拒绝、移除失败、查询失败、旧 service 回调隔离、外部改动刷新、
批准后以查询为准、完整列表解析、系统应用分类、两组设置优先排序和推荐包完整性的 JVM 测试。
`check_settings_ui.py --scope-only` 在 debug 的模拟状态页面验证系统二级开关、
无设置应用的开关，以及独立的设置入口。它不代替真实 LSPosed 授权通知的设备验收。
